# TextKit 2 renderer stack

The TextKit 2 (TK2) text renderer is rebuilt as a stack of small PRs, each moving one more kind of content from SwiftUI `Text` onto TK2 until the two renderers reach parity. Until a kind moves, it keeps rendering through SwiftUI, so every intermediate state ships a correct document. This file is the living plan for the stack: the switch, the PR order, what each PR covers, the parity inventory, the contracts later PRs build on, and how to run the gates.

Companion documents: `Architecture-Decisions.md` §21 (the decision record), §2 (why SwiftUI `Text` was the original choice), and §4, §16, §18, §20 (lazy-row invariants every TK2 row must respect). In this file, "ADR §N" means a section of `Architecture-Decisions.md`; a bare "§N" means a section of this file.

Parity reference: **main's SwiftUI rendering**. Every pixel diff, height check and behaviour check compares against a Release build of main; main's screenshots are the final authority.

---

## 1. Purpose and the renderer switch

TK2 exists to unlock what SwiftUI `Text` cannot do in a reader: continuous text selection across blocks with native handles (§5), and finer control over layout, hit-testing and highlight painting. It must get there without regressing the scroll performance and the lazy-row invariants the SwiftUI renderer established.

**TK2 is OFF by default.** The SwiftUI renderer remains the shipping path until a separate ON-by-default decision is taken after the stack reaches parity.

### Public API

```swift
public enum ADFTextRenderer: String, CaseIterable, Sendable, Identifiable {
    case swiftUI = "swiftui"
    case textKit2 = "textkit2"
}

ADFDocumentView(model:mediaProvider:interactionHandler:taskStates:mentionContent:
                textRenderer: ADFTextRenderer = .swiftUI)
```

- `ADFTextRenderer` lives in `Sources/ADFRendering/TextKit2/ADFTextRenderer.swift`; `displayName` gives "SwiftUI" / "TextKit 2" for a host's picker.
- `ADFDocumentView` passes the choice to each `DocumentRow`, which sets the internal `EnvironmentValues.adfTextRenderer` to the host's choice **only for top-level `.richText` and `.listRows` rows** (`TextKit2Scope.inheritsRenderer`, `ADFDocumentView.swift:314-322`; a list only when it passes the list rules, §3 "PR 2: lists") and to `.swiftUI` for every other kind, so the value never leaks into a container's children. A list row is the only other setter: it passes the choice to its own text and resets every other trailing block to `.swiftUI` (`ListBlockView.swift:78`). `TextKit2RendererSetterTests` scans `Sources/` and requires exactly these two setters.
- One shared leaf, `TextEngineLeaf`, picks the engine with a plain `if`/`else` (never `AnyView`, never `#available` at a lazy per-item position — ADR §18); `RichTextBlockView` and a list row's leader both draw through it.
- On platforms without UIKit (`swift test` on macOS), `.textKit2` behaves as `.swiftUI`.
- **All public surface PR 1 adds:** `ADFTextRenderer` (+ `displayName`); the `ADFDocumentView(textRenderer:)` parameter; the diagnostics read-outs below (`ADFTextKit2Stats`, `ADFTextKit2Coverage`, `ADFTextRenderer.textKit2Stats`, `.textKit2Coverage(of:)` — public because the demo reads them across the module boundary); in `ADFPreparation`, `ADFFontSpec` (+ `Font(adfFontSpec:)`, `TextStyle.swiftUITextStyle`), the `adf` attribute scope carrying it, `ADFTheme.bodyFontSpec` / `codeFontSpec` / `headingFontSpec(_:)`, and `InlineComposer.compose(_:baseFont:baseFontSpec:)`. The small-text and sub/superscript specs stay internal, like their `Font` twins.
- **PR 2 adds no public type**, only defaulted fields on the two diagnostics read-outs, so PR 1 callers compile unchanged: `ADFTextKit2Stats.liveListRowCount` and `.conversionCount`; `ADFTextKit2Coverage.eligibleTextLeaves`, `.linkedTextLeaves`, `.fallbackTextLeaves`, `.listLeaderLeaves` and `.listTrailingLeaves` (§3, "Diagnostics and coverage").
- **From PR 3 a top-level `.codeBlock` row keeps the host's choice too** (`TextKit2Scope.inheritsRenderer`; the root setter is now at `ADFDocumentView.swift:314-322`). A code block has no children, so `CodeBlockView` only reads the value, for its code text, and adds no setter: the two setters above are still the only ones, and `TextKit2RendererSetterTests` still requires exactly two. `CodeBlockView` hands its code text to the same shared leaf, `TextEngineLeaf`. Code inside a list item gets `.swiftUI` from its row, and code inside any container gets it from `DocumentRow` (§3, "PR 3: code blocks").
- **PR 3 adds no public type** outside the diagnostics SPI. It adds defaulted fields on the two diagnostics read-outs, so PR 1 and PR 2 callers compile unchanged: `ADFTextKit2Stats.liveCodeRowCount` and `.codeNativeDrawCount`; `ADFTextKit2Coverage.eligibleCodeRoots` and `.fallbackCodeRoots`. It adds one public function, `ADFTextRenderer.textKit2CodeAdmission(of:dynamicTypeSize:legibilityWeight:displayScale:layoutDirection:)`, which returns the measured counts `admittedCodeRoots` and `gatedCodeRoots` as a tuple (public because the demo reads it across the module boundary), and three `@_spi(ADFDiagnostics)` read-outs: `ADFTextRenderer.textKit2CodeRowDraws` and, for the visual gate's capture geometry (`c6c518d`), `ADFTextRenderer.textKit2RowFrames(in:)` with its value type `ADFTextKit2RowFrame` (UIKit only) and `ADFDocumentModel.fullyVisibleRowIDs`. In `ADFPreparation`, the code shape `ADFCodeShape` and its attribute key `adfCodeShape` have `package` access and are not public API; a prepared code string also carries the existing public `adfFontSpec` attribute (§3, "PR 3: code blocks", "Diagnostics and coverage").
- **From PR 4 the container kinds the container allow list holds keep the host's choice too, and a third setter exists: the container boundary.** `DocumentRow` passes the choice to a top-level panel, quote, bodied extension placeholder, layout section, expand or captioned media when its kind is in `TextKit2Scope.containerChildKinds` and it passes its whole-block rule (`TextKit2Scope.inheritsRenderer`); it is still the only root setter. Inside a container, `View.adfContainerChild` (`TextKit2ContainerBoundary.swift`, applied at the five child sites) sets each child's renderer, never turning TextKit 2 back on below a row or a container that reset it. `TextKit2RendererSetterTests.threeSetters` (`TextKit2ListScopeTests.swift`) scans `Sources/` and requires exactly three setters, in `ADFDocumentView.swift`, `ListBlockView.swift` and `TextKit2ContainerBoundary.swift` (§3, "PR 4: containers and captions").
- **PR 4 adds no public type and no public modifier.** Its styling value, `EnvironmentValues.adfTextForeground` (the caption's `.secondary`), is internal, with one setter. Public surface it changes, all diagnostics: defaulted fields on the two read-outs, so PR 1–3 callers that construct or read them compile unchanged (`ADFTextKit2Stats.liveContainerRowCount`, `.containerNativeDrawCount`, `.containerTextKit1DrawCount`, `.liveCaptionRowCount`, `.captionNativeDrawCount`, `.liveOffWindowRowCount`; `ADFTextKit2Coverage.eligibleContainerLeaves`, `.linkedContainerLeaves`, `.fallbackContainerLeaves`, `.containerListLeaves`, `.eligibleCaptionLeaves`, `.fallbackCaptionLeaves`, `.eligibleNestedCode`, `.fallbackNestedCode`, `.unpreparedExpands`); two `@_spi(ADFDiagnostics)` per-owner records, `ADFTextRenderer.textKit2ContainerRowDraws` and `.textKit2CaptionRowDraws`; and one public function, `ADFTextRenderer.textKit2CodeAdmissionIncludingNested(of:dynamicTypeSize:legibilityWeight:displayScale:layoutDirection:)`, which returns PR 3's root pair (`admittedCodeRoots`, `gatedCodeRoots`) and the same split of the code below containers (`nestedCodeAdmitted`, `nestedCodeGated`). PR 3's `textKit2CodeAdmission(of:…)` keeps its two-element tuple, so a caller that destructures it into two values compiles unchanged (code review A-Q2 reversed a draft that widened that tuple to four elements); the demo reads the new function.

### Proving which renderer ran

A launch flag or a toolbar label never proves TK2 executed. `TextKit2Diagnostics` (internal, main-actor singleton) counts live rows, layouts, draws and **native draws** (draw passes in which TextKit 2 itself drew layout fragments), process-wide; each TK2 row sets `accessibilityIdentifier = "tk2-row:<ownerID>"`. Public read-outs: `ADFTextRenderer.textKit2Stats` (`liveRowCount`, `layoutCount`, `drawCount`, `nativeDrawCount`, `textKit1BackedRowCount`, `textKit1BackedDrawCount`) and `ADFTextRenderer.textKit2Coverage(of:)` (`eligibleRoots`, of which `linkRoots`; `fallbackRoots`, of which `textFallbackRoots` — paragraphs and headings kept on SwiftUI). **TextKit 1-backed rows are reported apart:** a row whose text has a link is a TK2 row (`tk2-row:<id>`, counted live) whose own TextKit 1 stack lays out and draws the text (§6.4), so its draws count in `textKit1BackedDrawCount` and never in `nativeDrawCount`; a draw is one or the other, never both. A gate that must prove TextKit 2 rendering requires `nativeDrawCount > 0`; every perf and coverage table states the TextKit 1-backed share (stress-5k 507 of 2,400 eligible roots, text-dense 808 of 3,000). Unit tests assert eligible rows create TK2 rows and ineligible ones do not, and that switching back releases them (the test's own row instances leave the window, and dropping its references lowers the live count by exactly their number). Suites run in parallel, so tests check their own hosted rows and compare a process-wide counter only across a span with no suspension; the XCUITest asserts `tk2-row:<id>` and `tk2-live-rows` in both directions.

**From PR 2**, list text is proved apart: `liveListRowCount` counts the live rows drawing list text (a top-level heading drawing natively proves nothing about lists), a list leaf's row is `tk2-row:<PreparedListRow.id>` and a list paragraph's `tk2-row:<its block id>` (owners below root level, `0.<n>.…`), and the leaf coverage counts list leaders and list paragraphs apart from roots (§3, "Diagnostics and coverage"). Coverage is static — potential coverage: it does not know an active search or the host's text environment — so the execution proof is always the live counters and row identifiers.

**From PR 3**, code is proved apart, and per owner. `liveCodeRowCount` counts the live rows drawing a code block's code, and `codeNativeDrawCount` the native draw passes of such rows, counted where TextKit 2 drew at least one layout fragment: a live code row that has not drawn does not count, and a paragraph or list row drawing natively proves nothing about code. A code row is `tk2-row:<RenderBlock.id>`, a root-form owner (`0.<n>`) like a root paragraph's, so the identifier alone does not tell the two apart: the UI tests tell a code row by its place inside the block's horizontal scroll view (`DocumentSnapshot.codeOwnedRows`; `rootOwnedRows` excludes code rows since PR 3). For one named block there is a per-owner record, `ADFTextRenderer.textKit2CodeRowDraws` (`@_spi(ADFDiagnostics)`; the demo prints it as `TK2_CODE_ROWS`): for each owner with a live code row, the native draw passes that row has dispatched since it came alive. A live row that has not drawn is listed with 0, a block whose code is on SwiftUI is absent, and an entry goes when its row is released. A count says the row drew, not that it is on screen at that instant: a live row prefetched off screen is listed too. So in a document that mixes code with other text a gate must name the visible code owner and require its entry with draws above zero; a global native count is not enough. The entry does not say where the row is, so the visual gate also reads the screen at the moment of its screenshot (`-captureGeometryHook`, §1 "Demo app"; `c6c518d`, `6d6a2c2`): each TextKit 2 row's window frame and the rows the reader reports fully visible. It accepts a declared code owner only where that owner's own row's on-screen frame holds the code pixels it scores (§8.2). The record is keyed by owner id alone: two live rows with one id (two documents at once, or a replaced document whose rows are still alive) share one entry, which adds up their draws and goes when the last of them is released. So it proves one document at a time. The code coverage is in two parts that must not be confused. `eligibleCodeRoots` and `fallbackCodeRoots` are static and content-only. Whether an eligible block is really drawn by TextKit 2 also depends on where it is drawn (layout direction, and the canvas bound at the text size, legibility weight and display scale, §6.6), which the static walk assumes favourable; `textKit2CodeAdmission` measures it at an explicit environment (`codeAdmitted=`, `codeGated=`). Neither part knows an active search or inherited `Text` styling, so the execution proof is still the live counters, the per-owner record and the row identifiers.

**From PR 4**, container text and captions are proved apart, and per owner, the same way. `liveContainerRowCount` counts the live rows drawing text below a container boundary (prose and nested lists; never code, which counts as code wherever it sits), `containerNativeDrawCount` their native draws and `containerTextKit1DrawCount` the draws of their linked, TextKit 1-backed rows; `liveCaptionRowCount` and `captionNativeDrawCount` do the same for captions. A nested list row counts in both `liveListRowCount` and `liveContainerRowCount`. `textKit2ContainerRowDraws` and `textKit2CaptionRowDraws` (`@_spi(ADFDiagnostics)`; `TK2_CONTAINER_ROWS`, `TK2_CAPTION_ROWS`) are per-owner records with `textKit2CodeRowDraws`' semantics and its one-document limit. `liveOffWindowRowCount` counts live rows on no window, the lifecycle's second OFF check (§6.7). The UI tests classify each `tk2-row` by its owner and place (`RowOwnerTables`, `TextKit2RowClassifierTests`), because a container owner `0.<n>.<m>` cannot be told from a nested list paragraph by its identifier alone. The coverage stays static and stacked: it counts layout columns as stacked and never enters an expand body (`unpreparedExpands`), so on a regular-width device, and for open expand bodies, the execution proof is the live counters and the per-owner records.

**Performance is gated in every PR against main** (§8). There is no separate performance PR, and a PR that fails its gate on a row it introduces is fixed before review. **Known debt** is the one exception, and it is a label, never an allowance: PR 2 shipped with a disclosed arm-C failure (list-dense and kitchen-sink with TextKit 2 ON; https://github.com/bharath2020/connie-adf/issues/10), accepted by the captain. A later stage that contains the same code carries those rows forward as known debt: they are still reported as FAIL, the stage's verdict says so, and the stage must not make them worse (a paired comparison against its predecessor, §8.3). A known-debt label never covers a missing proof, a new row, a crash or a timeout. Each PR adds its feature-dense fixture and interaction checks to the gate cumulatively.

## 3. PR 1 coverage and fallbacks

### What TK2 draws in PR 1

A top-level `.richText` block (paragraph or heading H1–H6) when **all** of these hold:

1. the switch is ON (`.textKit2`);
2. the block contains no inline atoms (`SegmentedTextView.mergedText(segments)` is non-nil);
3. every run is *describable* — it carries an `ADFFontSpec` (§6.5), so TK2 can resolve the same font SwiftUI would;
4. before iOS 26, the text does not end in two or more hard breaks (residual found on iOS 18.5, §6.4);
5. no inherited `Text` styling the row does not reproduce is set — line spacing, text case, a line limit, a minimum scale factor or redaction (`TextKit2Leaf`);
6. the active search has no highlight for the block (`TextKit2Leaf`): while a session has spans for it, it renders on SwiftUI, which paints the highlights and the arrival flash; clearing the search returns it to TK2 (heights are equal, so the swap moves nothing).

Text-run content in such blocks moves with them: every mark (strong, em, underline, strike, code, sub/sup, textColor, backgroundColor, link, annotation, small font size), hard breaks, emoji that carry a Unicode `text`, and inline placeholders. Because the preparer flattens them to top-level `.richText`, three less obvious sources are also eligible: the content of a `syncBlock` with an inline copy, a stray `caption` outside a `mediaSingle`, and an inline node at block level.

### What stays on SwiftUI in PR 1

- **Atom paragraphs** — any paragraph containing a mention, status, date, inlineCard, emoji without text, mediaInline or inlineExtension renders whole via SwiftUI.
- **Links are disclosed, not native, in PR 1:** a paragraph or heading with a link is a TK2 row laid out and drawn by its own TextKit 1 stack, as `Text` lays out linked text (captain decision; §6.4). Native TextKit 2 links are PR 6.
- **Two or more trailing hard breaks before iOS 26**, and text under inherited styling the row does not reproduce (condition 5 above).
- **Every other kind and every nested position** — lists (PR 2, below), code blocks (PR 3, below), tables (including the pinned header slice), panels, quotes, expands, layout columns and all of their contents, media captions, extension placeholders, custom (plugin) blocks and unknown nodes.
- **Search highlights and arrival flash** — TK2 rows do not paint them yet (PR 7); a block with highlights renders on SwiftUI while the search is active (condition 6 above).
- **Text selection and copy** — TK2 rows have none yet (PR 8). SwiftUI rows keep per-block `.textSelection(.enabled)`. This is an explicit, temporary limitation of the opt-in TK2 arm.
- **Undescribable themes** — a theme built from raw SwiftUI `Font`s without specs falls back (§6.5).

### PR 2: lists

Evidence paths in this subsection and in §6.7 are under PR 2's task data directory (`<data>`).

#### Scope and boundaries

- **Roots.** `DocumentRow` passes the host's choice to a top-level `.listRows` block as it does to `.richText` (`TextKit2Scope.inheritsRenderer`, `ADFDocumentView.swift:314-322`), subject to the list rules below. The preparer flattens nesting (`ListPreparer`): a nested list becomes deeper rows of its root list, so "nested lists" means every depth row of a root list, under one policy at every depth.
- **The list child boundary.** A list row is the only other place the renderer is set. When the row keeps the renderer (rule A below), it passes the choice to its leader and to the paragraphs and headings in its text column; it sets `.swiftUI` on every other trailing block, and so on that block's whole subtree (`ListBlockView.swift:63-78`). The reset is required, not defensive: no container sets the key (panels, quotes, expands, layout columns, extension bodies and table cells recurse through plain `BlockView`), and an environment value flows to every descendant, so without it a panel inside a list item would inherit TK2. `TextKit2RendererSetterTests` scans `Sources/` and requires exactly two setters, in `ADFDocumentView.swift` and `ListBlockView.swift`.
- **Trailing `.listRows`** occur even though a direct nested list is always flattened: a list inside a `syncBlock` (transparent to the preparer), a list under a malformed item child, and a non-`taskItem` in a `taskList` or a non-`decisionItem` in a `decisionList`. `TrailingListRowsOriginTests` pins all three (`Tests/ADFPreparationTests/ListFixturePreparationTests.swift`). Under the list rules below, the row holding one keeps all its text, and the trailing list, on SwiftUI (rule A); the list's other rows keep the renderer.
- **Out of scope:** lists and text inside panels, quotes, expands, layout columns, extension bodies, media captions and table cells stay SwiftUI with their container (PR 4 / PR 5). A list never turns the renderer on by itself.
- **One rule for views and coverage.** The views and the coverage walk (`TextKit2Scope.forEachLeaf`) decide through the same `TextKit2Scope` functions and the same eligibility verdict, so the leaf counts are the leaves the views may hand to TK2.

#### Owners

- **Leader:** `PreparedListRow.id` (the item's node path), passed through `TextEngineLeaf` to the TK2 row, `tk2-row:<row id>`. A task's interaction id still comes from `ListMarker.task(id:)`.
- **Continuation rows** (`<itemID>#cont<N>`, `ListPreparer.swift:110-118`) have empty segments, so no leader view. Their paragraphs are trailing `.richText` blocks owned by their own `RenderBlock.id`, never by the `#cont` id. `SearchIndexer` agrees: it keys the leader on `row.id` and walks each trailing block on its own.
- **Chrome:** bullets, numbers, checkboxes and the decision glyph are outside every owner's text and offsets (§5.1).

#### The shared text leaf and the leader style

`TextEngineLeaf` (`Sources/ADFRendering/TextKit2/TextEngineLeaf.swift`) is the one engine branch. Under `.textKit2`, text eligible where it sits (`TextKit2Eligibility.verdict(_:owner:)`) goes to `TextKit2Leaf`, which still makes the one engine decision (search highlights, unreadable inherited styling, the rebuild control); everything else draws the caller's SwiftUI fallback, and without UIKit the fallback always runs. `RichTextBlockView` keeps its indentation, alignment and heading wrappers around the leaf. `ListRowView` gives it the leader with the existing fallback, `SegmentedTextView(segments:ownerID:).textSelection(.enabled)`, and keeps its `HStack` / `VStack`, `@ScaledMetric` marker column, spacing, depth padding and decision background unchanged. It marks its text column `adfTextOwnerKind = .list`, which the iOS 26 gate and the live list counter read. The twenty-flip rebuild control (§8.3) goes through the same leaf, so it swaps exactly the list leaves TK2 swaps.

The leader is body text: `TextBlockStyle(font: theme.body, isHeading: false, headingLevel: nil, alignment: nil, indentation: 0, breakout: nil)` (`ListRowView.leaderStyle(theme:)`). The preparer composes a leader like a root paragraph and drops its block marks; the TK2 row reads only `alignment` and `isHeading` (fonts come from the runs' `ADFFontSpec`s), so nothing else needs to match. No inherited `Text` styling reaches a leader: its only modifier is `.textSelection(.enabled)`, task and decision colours apply to the marker glyphs only, and a done task is neither struck through nor dimmed. PR 2 is therefore not a caller of the §6.5 inherited-style contract.

#### When list text stays on SwiftUI: list rules and the iOS 26 gate

Each rule keeps text on SwiftUI rather than tolerating a difference. Each was found by measuring through the real `ListBlockView` / `ADFDocumentView` at actual column widths (`TextKit2ListParityTests`), and d109f70 narrowed rules A and B to the shapes measured to diverge in hosted-row probes at 3x and 2x, plus headings beside other text, which were measured at 3x only.

| Rule | Keeps on SwiftUI | Code | Measured cause |
|---|---|---|---|
| A | every text leaf of a row, and everything in its trailing blocks, unless its text column holds one text block (the leader alone, or a lone paragraph or heading) or only paragraphs, leader included, whose every run is in the body text style (plain, links, emoji, bold, italic, inline code). A column of one block has the height to itself and matched in every shape measured. Columns of body paragraphs matched in height and first and last baselines: every multi-paragraph row of list-dense and lists-parity (326 rows) at Large, xxxLarge, AX3 and AX5 on 375 and 320 pt documents, and synthetic shapes at xSmall to AX5 and Bold Text on four widths, at 3x and 2x. **iOS 26 gate (apart from A–D):** before iOS 26 all list text stays on SwiftUI. `TextKit2Eligibility.listsMatchText` is false there, so `TextKit2Eligibility.verdict(_:owner:)` returns `.fallback(.osGatedList)` for list text that would otherwise be eligible. The views (`TextEngineLeaf`, by `adfTextOwnerKind`) and the coverage walk both decide through it. Root paragraphs and headings keep PR 1's behaviour and pins. Precedent: PR 1's `trailingBreaksMatchText`. Cause: on iOS 18.5 (3x) the list suites had 131 real failures, mostly rows a pixel taller on TK2, which add up over lists and documents (`<data>/phase5/ios18-list-divergence.md`, §6.7).

Content fallbacks apply to list text as they do to roots (§3, PR 1): atoms, empty text (since PR 2 also text of hard breaks only, which draws nothing and whose baselines `Text` puts where no line metric does), undescribable fonts, two or more trailing breaks before iOS 26, unreadable inherited styling, and an active search highlight for that owner.

How the rules show in coverage: a row kept by rule A or a list kept by rule B is not walked, so its text is not counted as leaves at all. Rules C and D are decided when the view is built, and coverage assumes left to right and a column of at least 1 pt. The iOS 26 gate counts each gated leaf as a fallback. **Containers and code inside list items** are among what rule A keeps (a row holding any non-text block), so they are not counted either, and PR 4 leaves them there even where the list's own container migrates: moving them means reopening rule A, a follow-up stage that firstmate names after the core stack (P5). Lists inside containers are counted from PR 4, below a container boundary (`containerListLeaves`).

#### Layout passes per list leaf

A list leaf lays out **twice** on first materialisation; a root paragraph lays out once. The row's `HStack` sizes its flexible text column with a natural-width probe first (an unspecified proposal, laid out in an unbounded container and cached under `.infinity`, one of the row's four cache slots, §6.2), then proposes the column width (322 pt, or 286 pt one level down, in a 390 pt window). `TextKit2ListLayoutTests` pins this through the document view, per proposal (zero, narrow, phone, infinite, unspecified) and per materialised row. Measured at 1e778df over list-dense's then 3,686 eligible list leaves (iPhone 17 Pro simulator, iOS 26.3): probe ≈ 153 ms and column width ≈ 163 ms in total, so a list leaf's first layout costs about 1.9 times a root paragraph's (~42 µs more per leaf). This is not optimised in PR 2. The `pr2` gate failed arm C on list-dense, and reusing the probe's layout would save only about 5–10 % of the hitch-frame work (§6.6, §8.3). The baselines are unaffected, because the guides read the placed, bounded layout (§6.2).

#### The scope pattern later containers follow (PR 4, PR 5)

PR 2 fixes how the renderer choice enters a subtree, so containers reuse it rather than add a second mechanism:

1. The top-level kind joins `TextKit2Scope.inheritsRenderer`, with any whole-block rule it needs (as `listKeepsRenderer` for lists). `DocumentRow` stays the only root setter.
2. The container's view sets the key at its own child boundary: the choice for the text it migrates, `.swiftUI` for every other child and so its subtree, as `ListRowView` does. An environment value reaches every descendant, so a container that joins step 1 without this reset leaks TK2 into children not yet migrated.
3. `TextKit2Scope.forEachLeaf` follows the same rule, so coverage counts exactly what the views may draw.
4. `TextKit2RendererSetterTests` is updated, deliberately, to the new setter count and files.

### PR 3: code blocks

Evidence paths in this subsection and in §6.8 are under PR 3's task data directory (`<data>`).

#### Scope and boundaries

- **Roots.** `DocumentRow` passes the host's choice to a top-level `.codeBlock` as it does to `.richText` (`TextKit2Scope.inheritsRenderer`). Only the code text moves. The language badge, the Copy button, the padding, the grey box, the horizontal `ScrollView` and the search arrival flash are SwiftUI under either engine, unchanged (`CodeBlockView`). A breakout mark (`wide`, `full-width`) is still applied by `DocumentRow`.
- **No new setter.** A code block has no children, so `CodeBlockView` only reads the choice: of the scope pattern above it takes steps 1 and 3 (it joins `inheritsRenderer` and the coverage walk), step 2 (a reset at the child boundary) does not apply, and step 4 leaves the setter count at two. It marks its leaf `adfTextOwnerKind = .code`, which is not the renderer key.
- **Nested code stays SwiftUI, with no code change.** Code in a list item gets `.swiftUI` from its row (and list rule A keeps that row's own text on SwiftUI, unchanged). Code in a panel, quote, expand, layout column, extension body or table cell gets `.swiftUI` from `DocumentRow`'s reset, because no container sets the key. It moves with its container (PR 4 / PR 5). `TextKit2CodeScopeTests` hosts code in a list item, a panel, an expand, a quote, a layout column and a table cell under `.textKit2` and requires no `tk2-row` for it.
- **Wrapping does not change.** Code never wraps on either engine: the scroll view's viewport follows the width the block is given down to the shared chrome's minimum width, then matches SwiftUI's overflow (§6.2), and the text keeps its natural width, which is the scroll range.
- **Preparation changes attributes only.** `DocumentPreparer` stamps two attributes over the whole code string: `adfFontSpec`, from `theme.codeFontSpec` when the theme has one, and `adfCodeShape` (below). Block ids, block counts, `RenderBlock.Kind`, the characters and the SwiftUI font attribute are unchanged. A non-empty code string is still one uniform run; an empty one has no run and carries neither attribute. Every code block the preparer emits gets them, nested ones included, and with the switch OFF too: both ride the shipping path, and SwiftUI's `Text` ignores them. `CodeFixturePreparationTests` asserts all of this (ids and counts of the fixtures; the string without the two attributes is exactly the string main builds). In the visual smoke every A–B pair passed (`<data>/visual/detector-fix-0630.md`).
- **The prepared shape.** `ADFCodeShape` is a value-only summary of the code text, computed in one pass in preparation so that no view body ever scans code (ADR §2: views never compute): `lineCount` (line feeds + 1), `maxLineUTF16` (the longest line in UTF-16 units), `trailingNewlineCount`, `interiorEmptyLineCount` (the empty lines after the first line and before the last non-empty one), `isAllNewlines`, `isPrintableASCIIAndLF`, `hasTabs`, `hasNonASCII` and `hasOtherLineBreaks` (CR, VT, FF, NEL, U+2028, U+2029). Lines split at LF only: it is the one admitted line break. A non-empty code string that reaches a view without a shape (text assembled outside the preparer) fails closed to SwiftUI; nothing rescans it.
- **One rule for views and coverage.** The view and the coverage walk decide a code block's content through the same verdict (`TextKit2Eligibility.codeVerdict`), and the view-time rules are the same pure functions whether `TextKit2CodeGate` evaluates them or `ADFTextRenderer.textKit2CodeAdmission` does at an explicit environment.
- **Out of scope:** any wrapping change, syntax highlighting, line numbers, horizontal reveal of search matches, search highlight or arrival flash inside TK2 rows (PR 7), selection (PR 8), nested code, a tiled or viewport-clipped canvas, and a fix for PR 2's list cost (https://github.com/bharath2020/connie-adf/issues/10).

#### Owners

- **One owner per block:** `RenderBlock.id`, passed through `TextEngineLeaf` to the TK2 row, `tk2-row:<block id>`. Search spans and the arrival flash already key on it.
- Line feeds inside a code block are part of its owner's text; §5.1's separator applies between owners, not between lines.
- **Chrome:** the badge, the Copy button, the padding and the box are outside the owner's text and offsets.

#### The chrome adapter, the shared leaf and the code gate

`CodeBlockView` is the code block's **chrome and viewport adapter**. Its text-engine seams are `TextEngineLeaf` and `TextKit2Leaf`; everything around them is SwiftUI. The container stage (PR 4) reuses the whole view through `BlockView`: it does not wrap a second scroll view or a second Copy button around the leaf.

```text
DocumentRow                        the only root setter; a top-level .codeBlock keeps the host's choice
  BlockView -> CodeBlockView       chrome and viewport adapter, SwiftUI, unchanged
     header: badge + Copy          SwiftUI
     ScrollView(.horizontal)       SwiftUI; the viewport follows the proposed width (§6.2)
        TextEngineLeaf(text:)      the one engine branch (plain if/else); owner kind .code
           TextKit2CodeGate        only when ON and eligible by content: direction, canvas, empty lines
              TextKit2Leaf         search highlights, inherited styling, rebuild control
                 TextKit2RowView   natural layout, one per input generation; keeps its natural width
           fallback                Text(displayedCode).textSelection(.enabled), exactly main
        .padding                   SwiftUI
     grey box, arrival flash       SwiftUI
```

- **The leaf.** `TextEngineLeaf` has a second initialiser, `init(text:style:ownerID:allowsTextKit2:fallback:)`, for prepared text held as one string, so no segment array is built in a view body on either arm; the segment-based initialiser and its callers are untouched. With the switch OFF the leaf computes nothing and reads only the two environment values it read before (`adfTextRenderer`, `adfTextOwnerKind`).
- **The text it gets** is the stored `code`, never the highlighted copy. The fallback is exactly main's `Text(displayedCode).textSelection(.enabled)`. While the active search has highlights for the owner, `TextKit2Leaf` returns that fallback, so highlights and the arrival flash draw exactly as on main; the flash state stays in `Blocks/CodeBlockView.swift`.
- **The code gate.** `TextKit2CodeGate` sits between `TextEngineLeaf` and `TextKit2Leaf` on the code path only, and is constructed only when the switch is ON and the text is code. It reads the layout direction, the size category, the legibility weight and the display scale, so the SwiftUI arm reads none of them, and `TextKit2Leaf`, which every paragraph and list leaf goes through, gains no environment read. It is a plain `if`/`else` with no view state.
- **The style.** `CodeBlockView.codeStyle(theme:)` is `TextBlockStyle(font: theme.code, isHeading: false, headingLevel: nil, alignment: nil, indentation: 0, breakout: nil)`. The row reads only `alignment` and `isHeading`; the font comes from the code string's own `ADFFontSpec`.
- **The owner kind is semantic.** `TextKit2OwnerKind.code` is not a diagnostics label. It decides the verdict (the code rules, never a list rule or the list OS gate), the layout policy (`.natural`, §6.2) and the proof (a row counts itself by it). It says what the text is, not where it sits: a later stage that draws code inside a container keeps `.code` and adds the container's context beside it. Relabelling nested code as container text would make it wrap and bypass the code gate.
- **Shared with every TK2 row, with no new code:** the twenty-flip rebuild control (§8.3), the `tk2-row:<ownerID>` identifier and the accessibility exposure (§7).
- **One shared-row fix (`259b10b`).** `TextKit2RowView.init` sets its clear background inside `UIView.performWithoutAnimation`. During a rotation SwiftUI's lazy stack builds rows off-window inside UIKit's open animation block. The plain assignment added an animation that Core Animation could start twice and stop once, so XCTest's animation count stayed at +1 and every XCTest action waited 60 s (lifecycle C3's TK2 arm, 7 of 22 runs; `<data>/rot-debug/report.md`). Nothing animated on screen. The line is PR 1's; PR 3's dense code rows are what make a rotation build many such rows. The fix reaches every TK2 row (root, list and code) with no visible or layout change. `TextKit2RowViewTests.rowBuiltInsideAnimationBlockAddsNoAnimation` fails before and passes after on iOS 26.3 and 18.5; C3 then passed 3 of 3 with no stall (`<data>/init-fix/`). `TextKit2CanvasView.init` has the same assignment and keeps it: a control run showed the canvas never gets the animation (C44).

#### When code stays on SwiftUI

Each rule keeps the code on SwiftUI exactly as on main, by a named reason. The prepared string is never modified: no tab expansion and no newline normalisation, so the Copy bytes are the prepared string's on both arms.

Content rules, in the order `TextKit2Eligibility.codeVerdict` applies them. The verdict is constant time: it reads the first run's attributes and the prepared shape, never the characters.

- **The basis of these rules differs from PR 2's.** The list rules were each found by measuring a difference. The code content rules from `.proportionalCode` to `.codeControls` were not: they are the edge of the **admitted cohort**, the only class of code for which the canvas bound is a proven upper bound (every scalar printable ASCII, U+0020 to U+007E, or LF, in one fixed-pitch monospaced font). A shape outside it stays on SwiftUI because no conservative bound is proven for it, whether or not it would match `Text`. The parity suite still records how those shapes compare (`TextKit2CodeShapeExperiments`, record only, `CODE_E2` lines in `<data>/step4-tests/` and `<data>/step7-tests/`). Forced onto the row at Large and AX3, on 3x and 2x iOS 26.3 and on iOS 18.5, tabs, emoji and CJK, combining marks, Hebrew and Arabic, CR, CRLF and U+2028 all matched `Text` in size, ink and pixels, and so did two or three trailing line feeds on iOS 18.5. But tabs and emoji or CJK text drew canvases wider than the bound (3x, Large: tabs 620 × 213 px against a bound of 570 × 336, emoji and CJK 843 × 147 against 696 × 270), which is why the bound does not cover them. PR 2's precedent, `listsMatchText`, keeps all list text on SwiftUI before iOS 26; this gate is narrower and keeps only the measured shape at the measured sizes, so before iOS 26 code with no interior empty line, and all code up to AX3, stays on TK2. AX4 was gated before it was measured (fail safe), and the AX4 probe then confirmed the difference. The code gate and `textKit2CodeAdmission` evaluate the rule with the same function.
- **A Text Size change can move a block across the canvas caps**, in either direction, because the size category is an input of the gate. - **How the rules show in coverage.** A content rule counts the block in `fallbackCodeRoots`. The view-time rules, the empty-line gate included, are not in the static counts, which assume a favourable environment (left to right, a canvas within the caps, and iOS 26 or a size up to AX3); `codeAdmitted` and `codeGated` measure them at an explicit environment. Search and inherited styling are known to neither.

#### Layout passes per code row

A code row lays out **once per stable input generation**: the natural layout in the unbounded container answers every positive proposal and every placement, and the baseline guides, drawing and rectangle conversion all read it (§6.2). A root paragraph also lays out once, at its proposed width; a list leaf lays out twice. A change of inputs (text, size category, display scale, legibility weight, layout direction, policy) lays out once more; a re-apply, a colour-scheme flip or a new owner id does not. `TextKit2CodeDiagnosticsTests` asserts it on a row asked directly and on the hosted `CodeBlockView`: `relayoutCount` 1 and cached widths `[.infinity]` on 3x and 2x iOS 26.3 and on iOS 18.5. E1 (`CODE_E1` lines, `<data>/step7-tests/r2a-3x-code.log`): asked directly, the row answers every proposal (nil, infinite, and 0.333 to 5,000 pt) with its one natural size, 399.667 × 174.333 pt for the eight-line sample at Large on 3x. In a replica of `CodeBlockView`'s scroll view the horizontal `ScrollView` proposed only a `nil` width (nil × nil, then nil × the height) at outer widths of 44, 120.5 and 370 pt, on both arms, so no finite positive width reaches the row from it.

#### Accessibility

- A TK2 code row is one element, like every TK2 row (§7): label = the code's plain text, line feeds included, traits `staticText`, value `nil`, identifier `tk2-row:<block id>`, and no custom action (linked code is not eligible).
- The language badge and the Copy button (labelled "Copy code") are SwiftUI chrome under either engine and keep main's exposure. Order: badge, Copy, code.
- In the app the two arms' trees match: `CodeRendererUITests/testCodeAccessibilityTreeMatchesSwiftUI` passes on 3x, 2x and iOS 18.5 (the same elements, types, labels, values and order; the code is one element whose label is the whole text under either renderer). XCUITest shows no traits or custom actions. In a unit-test host SwiftUI may build no tree; E5 then records the comparison as unobservable (a known issue), and whenever the SwiftUI tree lists an element, the TK2 tree must list it too (`7f66338`). On iOS 18.5 at 3x and on iOS 26.3 at 3x and 2x the hosted SwiftUI tree listed no element at all (`CODE_E5 arm=swiftUI count=0`, `<data>/step9-fix-tests/t1-ios185.log`, `t2-3x.log`, `t3-2x.log`), so that rule is not exercised in the hosted test: the badge and Copy elements are compared by the app's accessibility-tree test, and the Copy action by the Copy test. #### What the container stage (PR 4) inherits

- **The adapter.** `CodeBlockView` whole, through `BlockView`: chrome, viewport, engine leaf, fallbacks and the code gate travel together. The container stage proves the real nested placements (panel, quote, expand, extension body, both column modes) at a nonzero pan offset; PR 3 proves only that the adapter's viewport follows a narrow outer frame down to the shared chrome's minimum width and then overflows as SwiftUI's does (§6.2).
- **Stage-specific scope pins.** "Nested code draws no TK2 row" (`TextKit2CodeScopeTests`) and "exactly two setters" (`TextKit2RendererSetterTests`) pin this stage's scope; they are not permanent rules. PR 4 revises, deliberately, only the positive pins for the ancestors it migrates and the setter allow-list. The verdict, gate, bound, fallback and sizing tests are written against the code view and the row, not against a root position, and stay valid for nested code. Code in a list row stays excluded by list rule A even when a container around the list migrates.
- **The code kind and the layout policy** stay with the text (above); ancestry is added beside them.
- **The canvas gate, unchanged:** its conservative inputs (the prepared shape and the run's own prepared font spec, §6.6), its named reasons, and its behaviour across text sizes. The per-block caps say nothing about a container that holds many code blocks: PR 3 makes no aggregate memory claim, and a container-level mitigation, if one is needed, is a design of its own, not the removal of the code caps.
- **Coverage:** the legacy totals and the root-only code counts keep their meaning. Adding code does not invalidate the list proof's subtraction; adding container prose to the text-leaf totals would, so the container stage installs an explicit eligible-list count first.
- **Metric inputs travel together** (§6.5): a style channel that changes a code font's metrics must reach the admission bound and the render inputs in one change.
- **The per-owner draw record proves one document at a time.** It is keyed by owner id alone (§1). A stage that shows two documents at once, or relies on it across a document replacement, scopes it by document or row generation first.

#### Scope at every ancestor boundary

Following the scope pattern of PR 2 (above): a top-level container keeps the host's choice when its kind is in the container allow list and it passes its whole-block rule (`TextKit2Scope.inheritsRenderer`, `blockKeepsRenderer`); then each container sets its children's renderer at its own child boundary, `View.adfContainerChild(_:in:widthBound:)`, applied at five sites: `PanelBlockView`, `QuoteBlockView`, `ExpandBlockView` (the open body), the extension body (`CardBlockView.swift`) and `LayoutColumnContentView`. The boundary writes three values: the child's renderer (`TextKit2Scope.childRenderer`), the width bound the container computed for its children (`adfTextWidthBound`, below), and the context `.container` (`adfTextContainerContext`, which the leaf's verdict reads). `childRenderer` passes `.textKit2` only when the container itself inherited it, the child's kind is in the allow list, the child passes its whole-block rule, and no view-time container rule fires (`containerGate`). It never turns TextKit 2 back on below a row or container that reset it; where the container inherited `.swiftUI` it writes the bound as `.pending`, so no SwiftUI child reads the container's width arithmetic (the five container views still compute their own bound on that path; nothing below them uses it, and the drawing does not depend on it).

- **The allow list:** `TextKit2Scope.containerChildKinds = [.richText, .panel, .quote, .extensionPlaceholder, .media, .expand, .layoutColumns, .listRows, .codeBlock]`. Pinned by `TextKit2ContainerScopeTests.topLevelRowsReadTheAllowList`.
- **Never in a container's TextKit 2 scope:** `containerExcludedKinds = [.tableSlice, .custom, .divider, .mediaStrip, .card, .unknown]`. A table (PR 5), a plugin block, a media strip, a card, a rule or an unknown node gets `.swiftUI`, and so does everything inside it.
- **Setters:** three, pinned by `TextKit2RendererSetterTests.threeSetters` (§1). The same test pins that only `CodeBlockView` and `ListBlockView` write the owner kind, only the boundary file writes the context, and nothing writes `adfContainerChildKinds` (the allow list as an environment value, read by the boundary; tests run the views under a narrower list).
- **Coverage follows the same rules** (`TextKit2Scope.forEachLeaf`), with two simplifications that make it the static potential, not the execution: it counts layout columns as stacked, left to right, column by column, and it never enters an expand body (it counts the expand in `unpreparedExpands` instead).

#### One shared-row change: a re-proposed reported width keeps its layout (B′)

The container sweep found a defect in the shared row itself, not in any container, and PR 4 fixes it there, in its own commit `54f4b0f`: **a change to PR 1's root rows** (call C53; code review F-R4, F-Q1).

- **The mechanism (D3).** A panel's child width can sit a few ulps past a device pixel, because the measured icon width enters the arithmetic (225.66666666666669 pt at 3x). A line ending in a space measures past the width, so `Text` and the TK2 row both report the next pixel, 226.0 (`proposalCeil`), with the same 9 lines. SwiftUI then places the row by proposing 226.0 again. Laid out anew there, the row fitted one more word on a line and came out 8 lines, centred in the slot measured first: equal height, baselines a line low. `Text` keeps its 9 lines. Proposed 226.0 fresh, both give 8 lines.
- **Where it appeared** (before the fix; each leaf hosted alone at the width its containers give it, iOS 26.3, 3x): at real widths in panel bodies only, at every size (xSmall 1, small 1, medium 1, xLarge 4, xxLarge 6, xxxLarge 1, AX3 4, AX4 5, AX5 8; `fixP/logs/t-w1`, `t-w6`, `t-w7b`). Quote, expand and extension bodies and stacked columns have whole-point insets and showed none at real widths; at off-grid widths (268–276 pt in thirds of a point) they did: 8 in 35,114 measurements at Large (3 panels, 4 quotes, 1 stacked column; `t-wfine1`). D3 needs an off-grid width and a word that fits in the extra pixel; the text size does not matter, so no size rule covers it.
- **The fix.** `TextKit2RowView.layoutResult(forProposedWidth:)`: a `.root` row (a paragraph or heading drawn by `RichTextBlockView`: at the top level, in a container or in a caption) proposed exactly the width it reported for a narrower bounded proposal answers with that proposal's layout, as `Text` keeps its layout under `RichTextBlockView`'s flexible frame. Since the delta review (D-R6, Astra R1; `a06e6ff`) it fires only when the row's last bounded wrapping measurement (`lastBoundedMeasurement`, cleared with the cache) was that narrower proposal: a bounded measurement at any other width in between makes the reported width lay out anew. Natural-size and zero-width proposals are not bounded measurements and change nothing. `.list` rows keep laying out anew: a list that grows to a row's reported width proposes every row that width again, and `Text` lays out anew there. Plain B, which covered list rows too, broke `TextKit2ListParityTests`' whole-document case (lists-parity at 385.333 pt, AX1, one 14,150 px band; `t-eB2`).

#### The width bound

`adfTextWidthBound` (`TextKit2WidthBound`: `.pending`, `.atLeast(width)`, `.unproven`) replaces PR 2's `adfListWidth`. It decides **eligibility only**: no leaf lays out at it, and the rows still lay out at the width SwiftUI proposes. `DocumentRow` seeds it from the row's content width (`TextKit2WidthBound.rowSeed(container:breakout:margin:)`; `.pending` until the column width is known, which is permissive). Each container narrows it for its children by its own insets: a panel by `spacing × 4.5` plus the scaled icon width (`iconWidthBound`, a `@ScaledMetric` of 28 pt; `.unproven` under the conditions above), a quote by `spacing × 2`, an open expand body by `spacing × 2.5`, an extension body by `spacing × 3`; a stacked column passes it unchanged (each column is proposed the section's width) and a side-by-side column passes its share (`ProportionalColumnsLayout.columnWidths`). A list row reads it as before (`listTextFits(widthBound, inset: textColumnInset)`), and a paragraph's own indentation is its inset (`RichTextBlockView`). `TextKit2ContainerWidthTests.boundIsLowerBound` proves it is never above the width the leaf is really proposed. Code ignores it: nested code keeps PR 3's `.natural` layout and its own gate; its viewport follows the container (below).

#### Lists in containers

A list in a quote, an extension body, an open expand body or a stacked column runs PR 2's rules unchanged at the nested bound: A (`rowKeepsRenderer`), B (`listKeepsRenderer`), C (left to right), D (`listTextFits`) and the iOS 26 list gate. Not enabled: a list in a panel (the panel shape rule), a list in a side-by-side column, and, at the accessibility text sizes, a list below any container (`.nestedListSize`). `TextKit2ContainerListTests` holds the parity matrix (`nestedListInQuote`, `nestedListInExtensionBody`, `nestedListInExpandBody`, `nestedListInStackedColumn`) and the scope cases (`rejectedListRowKeepsDescendantsSwiftUI`, `rtlListInContainerStaysSwiftUI`, `narrowNestedListStaysSwiftUI`, `nestedListAtAccessibilitySizeStaysSwiftUI`, `nestedListBeforeIOS26StaysSwiftUI`); `TextKit2ContainerWidthTests.firstScreenNestedListConvertsOnce` checks that the first screen's nested list owners convert once each. At the accessibility sizes every list below a container stays SwiftUI (`.nestedListSize`, code review M1, which replaced an earlier known issue): a list given 268 pt at AX4 puts its last baseline 28 pt from `Text`'s in a quote, an extension body, an expand body and a stacked column, and alone, so the cause is PR 2's list leaf, whose root rules are unchanged (§6.9).

#### Code in containers

A code block in a quote, an extension body, an open expand body, a stacked column, or a panel whose only child it is, is the whole PR 3 adapter (`CodeBlockView` through `BlockView`): chrome, viewport, engine leaf, content fallbacks and the code gate travel together, and its viewport follows the container's width. Code beside another block in a panel stays SwiftUI (the panel shape rule), so the code-parity capture of CP-26, a panel holding a paragraph and code, stays SwiftUI. Code in a side-by-side column, a list item or a table cell stays SwiftUI. Before iOS 26 nested code is `.osGatedContainer` before any content reason (`containerCodeVerdict`). The code counters count nested code: `tk2CodeLive` and `tk2CodeDraws` include it, and the coverage counts it apart (`eligibleNestedCode`, `fallbackNestedCode`; `textKit2CodeAdmissionIncludingNested` returns `nestedCodeAdmitted` and `nestedCodeGated` beside the root counts; `textKit2CodeAdmission` keeps PR 3's root pair). `TextKit2NestedCodeTests` covers narrow proposals, exact copy bytes, the pan offset across a switch, re-entry, the over-budget fallback, several code blocks in one quote (`eagerMultiCodeContainer`: 6 rows, 6 admitted and 1 gated, 9,381,312 summed nominal canvas bytes at 2x; §6.6), a zero-percent column, and the positions that stay SwiftUI. The canvas caps stay per block; there is no aggregate container cap (§6.6).

#### Expand bodies

A closed expand draws no body. When it opens, `ExpandBlockView` prepares the body off the main actor and keeps it in view state (`preparedBody`, `@State`), and its children go through the boundary like any container's. Coverage does not enter expand bodies (`unpreparedExpands` counts the expands it skipped), so lists and code inside them are not in the static counts. The search indexer does prepare closed bodies, to index them (§5.3). An open body converts each eligible leaf once: 300 conversions and 300 layouts for a 300-row body on a reopen and on each ON flip (`tallExpandBodyMount`, §6.6). Known defect, the same on main: an expand whose content is replaced shows the old body until it closes and reopens (§6.9, baseline issues).

#### Captions and the inherited foreground

A non-empty caption is a static leaf, `MediaBlockView.caption(_:ownerID:layout:theme:)`: a `TextEngineLeaf` owned by the media's id (the owner search already highlights) whose SwiftUI branch is main's `SegmentedTextView(…).font(.footnote).foregroundStyle(.secondary)`, wrapped in `adfCaptionLeaf()`. Three measured facts decided the shape (`TextKit2CaptionParityTests`):

1. **No font member.** Every prepared caption run carries its own font spec, so `.font(.footnote)` changes no caption metric: `captionFontIsPreparedRunFont`, 384 cases at 3x, height and baseline delta 0.000 with and without `.footnote`; the TextKit 2 row matches (64 cases are PR 1's residual 1, first and last ink rows equal; at 2x 13 such cases, worst 1 px).

3. **Every layout.** `captionFrameMatches`: 7 layouts × 24 cases (both directions, 200 pt and 66.66 %, Large and AX3, short, one-line and wrapping), 168 of 168 at 3x and 2x; the media-gallery sweep 60 of 60. So `captionLayoutKeepsRenderer` is true for every layout, and `Fallback.captionLayout` is wired but never fires. Since the code review the frame check is exact (F-R21: it allowed one device pixel of ink before); exact at 3x (`fixP/logs/t-w10`), PENDING(2x at the freeze); no iOS 18.5 caption run is needed, because captions there sit behind `.osGatedContainer`.

## 5. Cross-block selection architecture contract

Design only — PR 1 and PR 2 contain no selection code. PR 1 preserves what this contract needs (the owner id through the TK2 leaf) and states the limitation (TK2 rows have no selection or copy; SwiftUI rows keep per-block selection). Every adapter added in PR 2–6 must fit this contract.

PR 3 contains no selection code either. A TK2 code row has no selection of its own, the SwiftUI arm and every fallback keep per-block selection, and the Copy button works under both engines. What PR 3 preserves for this contract is listed in §5.6, and its one consequence for geometry in §5.4.

### 5.1 Addressing

A selection endpoint is a **document address**: `(document generation, owner id, local text position)`.

- **Document generation** distinguishes documents: structural ids (`"0.2.1"`) recur across documents, so an address from one document must never resolve in another.
- **Owner id** is the stable id of the text-bearing unit: the block id for paragraphs, headings and code; `PreparedListRow.id` for list leading text (a continuation row `<itemID>#cont<N>` owns no text: its paragraphs keep their block ids); `PreparedMedia.id` for captions; cell block ids inside tables.
- **Local text position** is an offset into that owner's merged text.
- **Document order** of owners is the order of the prepared block list, depth-first through containers — the order in which the preparer emits them.
- **Separators** between owners are a paragraph separator (`"\n"`); copy emits it between consecutive owners.
- **Atoms** occupy exactly one position each (attachment character), reserved for PR 6.

### 5.2 Offset mapping

Prepared ranges are `Character`-based (`SearchIndex` spans), TextKit works in UTF-16. The contract: each TK2 row builds a per-run UTF-16 prefix table **once per materialisation**, from the same merged `AttributedString` its `NSAttributedString` is built from, and the same table serves search highlighting (PR 7) and selection (PR 8); neither builds its own.

**No table exists yet** (as of PR 2). Its first consumer, PR 7, builds it; PR 2 allocates none. The text builder stays single-pass (`TextKit2TextBuilder.attributedString(for:linkColor:)` walks the merged text's runs once, appending each), so the table can be derived in that same pass.

PR 3 allocates none either. A code row's text storage is the prepared code string unchanged, so a local text position in a code block is an offset into the prepared string, and the same single-pass builder serves it.

### 5.3 Ownership and lifetime

- The selection (anchor and focus, as addresses) lives in a **document-level state object owned by the model**, like `model.expandedBlocks` — never in a row. It survives rows collapsing to spacers and re-materialising.
- Rows **render their slice** of the selection: on materialisation a row asks the selection state for its owner's range and paints it; it never holds selection state of its own.
- A row collapsing is not a removal: the address stays valid. Only a change that removes or rewrites an owner (new document generation, a content revision at that owner) clamps the selection to the nearest surviving address.
- **Expand bodies (corrected in PR 4).** The search indexer does prepare closed expand bodies, to index them (`SearchIndexer`, the `.expand` case), so search finds text in a closed body. Selection does not address a closed body: selection and copy are WYSIWYG. An open body is prepared again by `ExpandBlockView` and held in that view's state (`preparedBody`, `@State`), not in the model, so it is not model-addressable today: PR 8 must give open bodies a model-owned address (the body's block ids from the same preparer configuration) before a selection can span them, and must clamp a selection when a body closes.

### 5.4 Geometry

- Rows produce **row-local** rects from their own layout result (§6.2).
- Conversion to viewport coordinates uses the row's frame in the scroll content, obtained on demand by the interaction owner.
- No persistent named-coordinate geometry inside rows, and no SwiftUI state bound to visibility callbacks (ADR §4's rejected per-row geometry tracking and the ADR §20 lazy-row livelocks).
- **A code row sits inside a second, horizontal scroll view (PR 3)**, so it can move without the document scrolling. The interaction owner must convert a code row's rects on demand and never cache them, and selection-driven horizontal autoscroll inside a code block is PR 8's to design. `TextKit2CodeAdapterTests` asserts now that a row-local rectangle converted to window coordinates shifts by exactly the pan distance, on 3x and 2x iOS 26.3 and on iOS 18.5.

### 5.5 Interaction owner

- Native selection handles require a `UITextInput` implementer. The design is **one document-level overlay object implementing `UITextInput` over the §5.1 address space**, not one text view per row.
- `UITextPosition` / `UITextRange` wrap document addresses; `firstRect(for:)`, `caretRect(for:)` and `selectionRects(for:)` delegate to the rows that are live and fall back to collapsed-row estimates only for rows outside the render region.
- **Copy assembles text from the prepared model**, not from live views, so a selection that spans collapsed rows copies correctly.

### 5.6 Spike acceptance (before PR 2)

The throwaway spike must show, on two TK2 rows:

1. native handles appear and can be dragged;
2. a drag that crosses a lazy-row exit (a row collapses to a spacer mid-drag) keeps the selection;
3. copy yields exactly the expected text, including the separator;
4. fling + CPU settle stays at ~0 % with a selection active.

Result → keep this contract or revise it here before PR 2.

**Result (closed 2026-10-30): contract kept as written.** The captain checked by hand that cross-row selection and Copy worked on the throwaway spike. That proves feasibility, not production acceptance: a drag across a lazy-row collapse, held-edge autoscroll, the exact copied bytes, revision clamping, switch lifetime, performance and VoiceOver remain unproven, and they are PR 8's obligations. No spike code ships.

The spike report's seven obligations for list adapters ("Contract verdict and obligations for lists", items 1–7 of `cadf3-sel-spike/report.md` in the task data store) are the source of PR 2's identity, geometry and marker-chrome rules. PR 2 meets those it can before selection exists:

1. Leader owner = `PreparedListRow.id`; task and decision text keeps its prepared ids; nothing is keyed by the mounted view or a row index.
2. Continuation paragraphs own their text by their own block ids, in depth-first prepared order (§3, PR 2 "Owners").
3. Rows keep no selection state or offsets (unchanged from PR 1).
4. No map is allocated, and the text builder stays single-pass (§5.2).
5. The TK2 row is the indented text view itself, with markers, gap and depth padding outside it, so row-local rects convert through its frame and no marker width enters a text offset.
6. Markers align on the row's first text baseline (§6.2); `TextKit2ListParityTests` compares first/last baselines to 0.01 pt and the marker's offset from the first text ink.
7. Registration with the document input owner and Copy from prepared text are PR 8.

PR 3 meets these for code before selection exists:

1. The owner is `RenderBlock.id`. Nothing is keyed by a mounted view or a row index.
2. The row's text storage is the prepared code string, unchanged: no injected or removed characters, no tab expansion and no trailing-newline fix-up (a shape that would need one is not eligible). A local text position is an offset into the prepared string.
3. A code block is one owner. Line feeds inside it are part of the owner's text; the contract's separator applies between owners.
4. The row keeps no selection state and no offsets. No offset map is allocated, and the text builder stays single-pass (§5.2).
5. The TK2 row is the code text view itself. The header, the padding, the box and the horizontal scroll view are outside it, so row-local rects convert through the row's frame.
6. A code row can move horizontally without the document scrolling, so its rects are converted on demand and never cached (§5.4).
7. Copy is already assembled from the prepared model, not from a view.
8. One layout serves measuring, placing, the baseline guides, drawing and rectangle conversion (§6.2), so later selection rects use the same geometry as the drawn text.

PR 4 meets these for container text, with two gaps PR 8 inherits:

1. Owners are block ids, as at the top level: a container leaf owns its text by its own block id, a nested list leaf by `PreparedListRow.id` or its paragraph id, nested code by its block id, and a caption by `PreparedMedia.id`. Nothing is keyed by a mounted view, a column index or a row index.
2. Rows keep no selection state and no offsets; the text builder stays single-pass. The inherited foreground is a render input, not text: it adds no characters.
3. The TK2 row is the text view itself: the container chrome (panel background and icon, quote bar, expand header, extension frame, column spacing, media box) is outside it.
4. Reading order is prepared order, columns column-major (`columnOrderIsColumnMajor`).
5. **Gap:** an open expand body lives in view state (§5.3).
6. **Gap:** captions have no selection on either engine today; PR 8 decides whether they join it.

## 6. Sizing and cache contract

### 6.1 Height invariants

Collapsed rows replay exact heights (`CollapsedRowHeight`), and the live switch swaps engines without re-measuring collapsed rows. Therefore:

- The TK2 row's size is a **deterministic pure function** of (content, width, size category, display scale, layout direction, legibility weight), computed in the same SwiftUI layout pass.
- The two arms' heights are **interchangeable**: the TK2 height must equal SwiftUI's for the same inputs. The height-parity suite proves this across the whole input matrix; it is never assumed.
- No self-invalidation and no layout feedback (ADR §16): never `invalidateIntrinsicContentSize`, never SwiftUI state bound to visibility. Ordinary `setNeedsDisplay` is fine.
- No `#available` / `AnyView` at a lazy per-item position (ADR §18); the engine choice is a plain `if`/`else` at the leaf.
- No string allocation in view bodies (ADR §2): the `NSAttributedString` is built once per materialisation inside the representable, memoized by render inputs.
- **Code rows (PR 3):** the size of a code row is the same pure function with the width taken out and the layout policy added: any positive proposed width gets the row's one natural size. `CollapsedRowHeight` already treats a code block's height as width-invariant and rescales it with the text size. Both stay correct only while code does not wrap and the two arms' heights are equal. Measured: the whole-view height and width were equal (0 pt difference) for every admitted shape, size and weight of the parity matrix on 3x and 2x iOS 26.3 and on iOS 18.5. In the app, lifecycle check C3 (Text Size 0 → 3 → 0 over cached heights near and far) tests it (§8.3).

### 6.2 Layout result and cache

`TextKit2LayoutResult` = width, height, first baseline, last baseline, line count, line-fragment frames with their text ranges, and ink bounds (from `renderingSurfaceBounds`).

- **Cache key:** (render-inputs hash including content revision, width, size category, display scale, direction, legibility). Bounded width cache: **4 entries, LRU**.
- **Proposals:** `nil` width → natural width (unbounded container; cached under the natural width); zero → `.zero` without layout; infinite → natural width. A list leaf meets both on first materialisation: its row's `HStack` probes the text column at natural width before proposing the column width, so it lays out twice where a root lays out once (§3, PR 2 "Layout passes per list leaf").
- **Re-sync before geometry:** the single `NSTextLayoutManager` may currently be laid out for a different width than a cached answer. On a bounds change and before drawing, the row takes the layout SwiftUI placed it from (`placedResult(for:)`: the cached bounded measurement whose reported *size* equals the bounds — height included, since two proposals that hug to the same width can wrap differently — else one of that width, else a fresh layout at `bounds.width`), sets the container to *that layout's* container width (wider than the bounds for a hugging row) and re-runs `ensureLayout` if it differs. Cached numbers are never used for geometry without that re-sync.
- **No eager layout on new inputs:** `apply` rebuilds the string and clears the cache; the next layout happens when SwiftUI measures the row or before it draws, never at the stale bounds width. Since PR 2 the colour scheme is not one of these inputs: a scheme change sets the row's `overrideUserInterfaceStyle` and repaints its canvas, keeping the string, the TextKit 1 stack, the cache and the laid-out container (§6.6).
- **Baselines:** the representable exposes `.firstTextBaseline` / `.lastTextBaseline` from the placed layout (the same lookup at the guide's size, so reading a guide never lays out again), equal to SwiftUI's for single- and multi-line text. PR 2's list markers align on the first baseline: `TextKit2ListParityTests` compares each row's first and last baselines to 0.01 pt and the marker's offset from the first text ink, through the real list views.
- **Covered by tests:** repeated and reordered proposals (A, B, A — height at A unchanged, draw geometry at A correct), content change at a stable row id, Dynamic Type change, teardown after switch or collapse, baseline exposure.
- **A re-proposed reported width (PR 4, B′, `54f4b0f`).** A `.wrapping` row whose owner kind is `.root`, proposed exactly the width it reported for a narrower bounded proposal, answers with that proposal's cached layout instead of laying out anew at the new width, as `Text` keeps its layout under `RichTextBlockView`'s flexible frame. Since `a06e6ff` (delta review D-R6) it does so only when the row's last bounded wrapping measurement was that narrower proposal. It is the one case where a wrapping row's answer is not a pure function of (inputs, width): it depends on the cache and on the last bounded measurement, which new inputs clear. `.list` rows and fresh proposals lay out anew. A TextKit 1-backed (linked) row still draws and hit-tests at its bounds' width, which is what `Text` draws (delta review D-R1, measured). Mechanism and evidence: §3, PR 4, "One shared-row change".
- **Layout policy (PR 3).** `TextKit2RenderInputs.layoutPolicy` says how a row answers a proposed width: `.wrapping` (the default: paragraphs, headings, list text) or `.natural` (code; from `TextKit2OwnerKind.layoutPolicy`). It is part of the cache key and of the rebuild decision, so changing it rebuilds. For `.wrapping` every rule above is unchanged: PR 1's and PR 2's parity, layout and sweep suites pass unchanged in the full runs on 3x, 2x and iOS 18.5, apart from the baseline failures listed in §8.1.
- **The selected-layout invariant.** Measuring, placing, the baseline guides, drawing, hit-testing and rectangle conversion all read **the selected placed layout**, and the container is set to *that layout's* container width, never unconditionally to `bounds.width`. For `.wrapping` the selection is `placedResult(for:)` as above. For `.natural` there is exactly one layout per stable input generation: the natural layout in the unbounded container, cached under `.infinity` (one of the four slots). It answers a `nil`, an infinite and every positive finite proposal, and every placement whatever size the row is placed at; a finite width of zero or less still answers `.zero` without layout. So a second layout at the hugging width, which could wrap a line that measures a fraction wider there while the reported height assumed it did not, never happens. New inputs (text, size category, display scale, legibility weight, layout direction, policy) clear the cache and lay out once more; a re-apply, a colour-scheme flip or a new owner id does not.
- **Natural rows are left-aligned with zero shift.** For `.natural` the builder sets the paragraph alignment to left whatever the inputs' alignment and layout direction say, so the alignment shift within the bounds is zero and the unbounded container needs none. Right-aligned or centred non-wrapping text needs a design of its own; right-to-left code stays on SwiftUI (§3, PR 3).
- **No-wrap depends on the canvas gate.** The unbounded container is 1,000,000 pt wide, which is finite. A code line stays unwrapped only because the code gate admits text whose width is bounded far below that (at most 8,192 px, §6.6). A `.natural` row built directly with a longer line would wrap at 1,000,000 pt.
- **Inner size and outer viewport.** A code row's own size is its natural content size, which is the scroll range. `CodeBlockView`'s horizontal viewport, not the row, takes the width a parent proposes: it follows the proposed width down to the shared chrome's minimum width (the header with the badge and the Copy button), then matches SwiftUI's overflow. `TextKit2CodeAdapterTests.narrowFrames` hosts the real `CodeBlockView` in outer frames of 320, 200, 120.5, 44, 8 and 1 pt and of one pixel. It asserts that the viewport is at most the larger of the frame and that minimum, that the content keeps its natural width and scroll extent (one layout, cached under `.infinity`), that a pan keeps its offset, and that both arms' viewports are equal at every frame. The minimum is the SwiftUI arm's viewport in a one-pixel frame: 54.667 pt for the eight-line sample at Large on 3x, so in a 44 pt frame both arms overflow the frame by the same amount. The proposal matrix in `TextKit2CodeDiagnosticsTests` (zero, nil, infinite, narrow, fractional and regular proposals; placement at a different frame height; A, B, A; same-id replacement; an appearance-only change) passes on all three runtimes. That is adapter testing; real nesting in containers is PR 4's to prove.

### 6.3 Line-pitch rule

- The TK2 row's height is a **measurement rule over TextKit's layout**, not a layout change: the first baseline already sits at the ascent, as in SwiftUI.
- Any correction must be **sign-correct** at every size category (leading is negative at the largest accessibility sizes) — never subtract a constant.
- The drawn area must never clip ink: the layout's ink bounds must lie within it. Covered by tests (`TextKit2RowViewTests` "the canvas covers the bounds and the ink's vertical reach", `TextKit2MetricsParityTests`), not asserted at runtime.
- Backgrounds, underline/strike, hit-testing and (later) selection rects use **the same geometry as drawing**.
- Monospaced runs resolve through the preferred text-style descriptor with `.monospaced` design, keeping ascent, descent and leading identical to body at every category. Fonts resolve with `UIFont.preferredFont(forTextStyle:compatibleWith:)`, never `UIFontMetrics` point scaling.

### 6.4 Line pitch and wrapping (measured)

Background, measured against fresh main before the fix (W = 370 pt, 3x, 70 probe cases):

- SwiftUI `Text` height = (N − 1) · (ascent + descent + leading) + ceil_px(ascent + descent); raw TK2 usage height = N · (ascent + descent + leading). At body / `.large` this made raw TK2 rows 1.667 pt taller per row, accumulating down the document.
- SwiftUI breaks one word earlier on nearly full lines (it avoids a single-word last line); line *counts* agree across strategies, so only per-line extents reveal the difference.

**Rules shipped in PR 1** (all measured against SwiftUI bitmaps and guides on iOS 26.3 at 3x and 2x, and on iOS 18.5; evidence under `<data>/parity/`):

- **Height** = ceil_px(last baseline + last-line descent), where a line's ascent/descent are the tallest/deepest run on it by its *font's* metrics — a fallback font's do not count (`Text` sizes "ab 🧪", "ab 漢字" and "ab नम" by the system font alone at 1600/1600 sizes, where Core Text's line bounds are taller) — and a baseline offset only ever grows them (a superscript's raise adds to its ascent, a subscript's drop to its descent). At 96778b3 (`TextKit2HeightParityTests`, the sub/superscript-line family included): 1,530/1,530 heights exact (worst |Δ| 0.0) on each of 3x, 2x and iOS 18.5, plus 510 RTL / Bold Text measurements and 156 corpus checks per device; the fixture sweep below.
- **Superscript lines** (`stress-5k` block 503: 3.33 pt short at large, 24 pt at AX3, every row below shifted on a renderer switch). TextKit 2 lets a raised run's offset eat its descent (a line set wholly in superscript gets none) and fits the line in the font's leading-inclusive line height; `Text` keeps the descent below the baseline and lets the raise eat only the run's leading. Read from `Text.Layout` line origins (offsets −4…12 pt, every pairing of plain/sub/superscript lines): below a line `Text` keeps the largest run descent + leading, a raised run's leading reduced by its raise (never below 0); negative leading (AX5) belongs to the next line's ascent, as in TextKit. The row moves every line below such a line by the difference (drawn line by line when moved). Run backgrounds: the band moves with the run's baseline offset beyond the one the whole line shares — a highlighted superscript among plain text rises with it, a line set wholly in it does not — and spans the Core Text ascent (a subscript lowers it). The suites' sub/sup family: first, middle, last and only lines, with colour, highlight, a hard break after it (the linked variants assert their SwiftUI fallback, `TextKit2FallbackTests`). The same escape explains the lifecycle gate's −26 px (−8.67 pt) shift on a switch made straight after a programmatic jump (`lifecycle/diag3`): an eligible row above Section 500, off screen but already laid out by the lazy stack, measured differently under TK2, and the scroll view keeps its raw offset; a gesture-parked view had other rows laid out above it. Replayed with the gate's own steps: −26 px (−36 px below block 503) at 0d7730e, 0 px at 9bf45ff for the menu switch, a menu open/dismiss, re-choosing the same renderer, About open/close and a UI-less flip. Not renderer-agnostic and not issue #6. Evidence: `<data>/jump-switch-c/`.
- **Fixture sweep** (`TextKit2FixtureSweepTests`): every TextKit 2-eligible root of kitchen-sink, stress-5k and text-dense at 370 pt, large and AX3, both arms, must measure within 0.01 pt — **no exemptions**; content the row cannot match exactly is not eligible. Linked roots are measured too (TextKit 1-backed). History: 46 escapes, worst 96 pt, before the superscript-line and fallback-font rules; at 9bf45ff 10,820 measurements with every residual a link+emoji paragraph 1 px taller (8 at 3x, 17 at 2x, 9 on iOS 18.5) — a default TextKit 1 stack counting the emoji face in line heights, which the row's stack no longer does (below). At 96778b3: 10,820 measurements per device, worst |Δ| 0.0 on 3x, 2x and iOS 18.5, no exemption (2 text roots stay on SwiftUI, both atom-bearing).
- **First baseline** is rounded to the nearest device pixel and the whole text is drawn shifted onto it (later lines keep their fractional offsets). Drawn unshifted, glyphs, underlines and strikes land 1 px low wherever the first baseline's pixel fraction is small (H1 at xxxLarge: 97.12 px). The row reports first/last baselines pixel-rounded too (16.187 → 16.333 at 3x), as `Text` does.
- **Line breaks:** `lineBreakStrategy = .standard`. 2,052 near-full Latin strings at large/xxxLarge × 370/640/353.333 pt matched per-line ink extents with `.standard` and `.pushOut` and missed 66 times with no strategy (one word later); 1,278 Korean, Japanese, Arabic and accented-Latin strings matched only with `.standard` (`.pushOut` alone missed 257 Korean strings — `.standard` adds Hangul word priority). In total 6,349 lines across 8 width/size sets, 0 mismatches.
- **Width hugging and alignment:** the reported width is the widest line, trailing whitespace included (left-to-right lines whose whitespace hangs past the container are measured with Core Text), pixel-ceiled, at most ceil_px(proposal) — `Text` reports 300.667 for a 300.5 proposal its whitespace overflows. ### 6.5 Inherited styling and themes

- `ADFTheme` gains spec-first construction; the SwiftUI `Font` is derived from the `ADFFontSpec`. A raw-`Font` initialiser stays source-compatible but marks the spec `nil` (undescribable); such runs force the SwiftUI path. No caller has to update two fields.
- `TextKit2RenderInputs` carries the text and the resolved inherited layout inputs — alignment, heading, size category, layout direction, display scale, legibility weight — and is the cache key and the rebuild decision. Since PR 2 the colour scheme is not among them: it is the row's paint input, applied apart (`TextKit2RowView.apply(_:colorScheme:ownerID:)`, §6.6).
- **No inherited colour channel in PR 1:** SwiftUI exposes no public getter for an inherited `foregroundStyle`, `tint` or font weight (the `EnvironmentValues` accessors are `package`), so a `UIViewRepresentable` cannot see what `Text` would inherit. Nothing in PR 1's scope (top-level paragraphs and headings in ADFReader) colours text that way, so PR 1 adds no channel; the first PR with an in-repo caller of inherited styling — containers (**PR 4**: media captions' `.footnote` / `.secondary`), then tables (PR 5: header weight, contrast foregrounds) — adds a library-owned environment value set next to the SwiftUI modifier it mirrors. **PR 4's outcome:** one internal value, `EnvironmentValues.adfTextForeground: Color?`, with one setter and one caller, the caption (`adfCaptionLeaf()`, next to the SwiftUI branch's `.foregroundStyle(.secondary)`; `inheritedForegroundHasOneSetter` pins it). The row applies it to runs with no colour of their own (`TextKit2RenderInputs.inheritedForeground`). A light/dark flip stays paint-only for it: the dynamic colour resolves at draw time, and a mounted secondary-foreground row flips light → dark → light without a rebuild or relayout, painting like fresh rows (`TextKit2AppearanceFlipTests`, case `secondaryForeground`). No font member was added: every prepared caption run carries its own font, so the caption's `.footnote` changes no metric (§3, PR 4). Weight ships with tables (PR 5).
- **Tint:** `Text` colours links with the tint, which a foreground style does not override; the row colours them with the accent colour (`Color.accentColor`, resolved at draw time). A host `.tint` around the document is **not readable** from UIKit (the accessor is `package`), so it recolours SwiftUI links only (§6.6).
- **Styling the row does not reproduce falls back:** readable `Text` environment — line spacing, text case, line limit, minimum scale factor, redaction — keeps the paragraph on SwiftUI (`TextKit2Leaf`, only built when the switch is ON). A `foregroundStyle` or font weight applied around the document is not readable and is not detected.
- Foreground precedence: a prepared foreground (author `textColor`, or the contrast colour derived from a background mark) first; then, for a link, the accent colour; then, from PR 4, the inherited foreground (`adfTextForeground`, a caption's `.secondary`); else `.label` (`TextKit2RowViewTests`, `foregroundPrecedence`).
- **Code metric inputs travel together (PR 3).** The code gate and the row resolve the same font from the same inputs: the code string's own prepared `ADFFontSpec` (never the ambient theme at view time), the size category and the legibility weight, through `TextKit2FontResolver`; the gate also takes the display scale and the layout direction, which are render inputs too. A later channel that changes a code font's metrics, such as PR 4's inherited weight, must reach the admission bound and the render inputs in the same change, and must not override the prepared code font. A paint-only input such as a colour reaches neither.

### 6.6 Known costs and limitations (PR 1 to PR 4)

- **Colour-scheme flip (fixed in PR 2, 7bafca1).** In PR 1 the scheme was a render input, so a light/dark flip rebuilt a byte-identical string and re-laid out every live TK2 row in one frame (`layoutCount` +1 per row per flip). The colours were never baked in: every colour in the string is a dynamic `UIColor` (`UIColor(foreground)`, the accent colour, `.label`), resolved when the canvas draws. Now the scheme is a paint input: a change sets the row's `overrideUserInterfaceStyle` and calls `canvas.setNeedsDisplay()`, never `rebuildText()`, and the text builder and colour conversion are unchanged. `TextKit2AppearanceFlipTests` flips one hosted row light → dark → light and compares it with fresh light and dark rows, pixel-exact, for plain `.label` text, an author-hex run, run backgrounds and an accent link (TextKit 1-backed); `layoutCount`, the row's relayouts, cached widths, the text instance, frame and baselines stay unchanged, and a flip together with a width or content change still lays out and rebuilds. The native TextKit 2 path needed no fragment-display invalidation.
- **Eager list roots multiply canvases (PR 2).** A top-level list is one eager `VStack` of all its rows inside one lazy row (ADR §4: nested content renders eagerly inside its block), so every eligible leaf of a materialised list root is a live TK2 row with its own canvas. list-tall (a 316-row root list and a one-row list) reported `tk2ListLive=317` at READY under `-textkit2` at 23f43cf. Virtualisation inside a list is unchanged (out of scope). Footprint ON vs OFF on list-tall (Fable F9; a pilot on the frozen candidate `cand-a76736f`, 2026-11-14, 3 pairs + 1 warm-up, iPhone 17 Pro simulator iOS 26.3, HOST-BUSY): with all 317 leaves live from READY to the end, TK2 ON (C) against OFF (B) on the same build is +3,616 KB at READY (medians 92,882 vs 89,266 KB) and +4,639 KB at the kernel peak (96,258 vs 91,619 KB, +5.1 %), about 15 KB per live row. Against main (88,178 / 90,370 KB) C is +5.2 % / +6.8 % and B +1.3 % / +1.3 %, and RSS moves by at most 1.6 %: all under the 15 % rule. A pilot gives no verdict, and its timing columns are not used; dropped frames and hitch were 0 in every trial of every arm, and C reported 634 layouts and 317 native draws. The simulator cannot see canvas memory, so these figures leave out the 317 canvases: their memory is the unmeasured device cost below, and a device run is the only real measurement. Evidence: `<data>/perf/pilot-list-tall-a76736f/` (`summary.md`).
- **List leaves cost frames on scroll with TextKit 2 ON (PR 2, accepted).** Each eligible list leaf is its own UIKit-hosted TK2 row and lays out twice (§3, "Layout passes per list leaf"): about 0.46 ms of main thread per leaf against 0.28 ms for `Text`. The cost lands in the frame where a list block materialises (5.9 TK2 leaves per block on list-dense); it is not a feedback loop or a per-frame relayout. With the switch ON, list-dense drops about 1.4–1.6 times the reference's frames, and PR 2's `pr2` gate fails arm C on list-dense and kitchen-sink; with the switch OFF every metric passes (§8.3 has the figures). Not fixed in PR 2: reusing the natural-width probe's layout would save about 5–10 % of the hitch-frame work and skipping the `AttributedString` compare about 2 %. The fix that would close the gap, one TK2 view per list row or block, is architectural (ids, accessibility, PR 8 selection) and is tracked as https://github.com/bharath2020/connie-adf/issues/10. TK2 stays OFF by default. Evidence: `<data>/perf/pr2-list-dense-c-diag/findings.md`.
- **TextKit 1-backed rows hold two stacks:** the TextKit 1 stack that lays out and draws the text, and the TextKit 2 layout that bounds its ink (stress-5k: 507 of 2,400 eligible rows).
- **Canvas backing stores:** each TK2 row draws into a non-opaque canvas sized to its bounds plus ink overhang (≈ 0.9 MB for a 353 × 70 pt row at 3x). This is Core Animation memory, which a live-malloc check does not see. Resting `phys_footprint`, C vs B on text-dense at fraction 0.5 (iPhone 17 Pro simulator, Release, 8 alternating launches, renderer confirmed by `RENDERER_STATS`, 7 live TK2 rows): medians 102,139 vs 99,923 KB, **+2,216 KB** (launch-to-launch spread ≈ 5 MB per arm), all of it malloc (TextKit objects); the CoreAnimation category is constant per arm (−320 KB in C) and IOSurface is 0 in both, so the simulator does not attribute the canvases' backing stores to the app at all. **The backing-store cost is therefore unmeasured: it needs a device run**, against SwiftUI's own text drawing layers as the B baseline (`<data>/memory-s11/`). The canvas cannot be opaque: it overhangs the row onto its neighbours and sits on container backgrounds.
- **Host `.tint` and inherited weight:** a host `.tint` recolours links in the SwiftUI arm only; TextKit 1-backed TK2 link rows keep the accent colour, and an inherited font weight is likewise not seen by TK2 rows (both accessors are `package`). PR 1 adds no API for them: the rest of the inherited-style contract (tint, weight) joins the explicit channel (§6.5) **no later than PR 4**. **Amended in PR 4**, under PR 1's own first-caller rule (decision S13: the channel member ships with its first in-repo caller): the foreground shipped in PR 4 with captions; weight ships with tables in PR 5 (header weight); host tint ships with its first host caller, and none exists in the repository. Until then TK2 link rows keep the accent colour. The phrase "no later than PR 4" is superseded by this rule.
- **Link + emoji + baseline offset at AX3+:** in a TextKit 1-backed row, a later line (not a paragraph's first) that has both a sub/superscript and an emoji may miss the negative-leading term at AX3 and above, because TextKit 1 sets the line it re-measures after a line separator as a first line (which drops negative leading). The row's height could then differ from `Text`'s by up to that line's negative leading; this is not measured, since no root in the three sweep fixtures has such a line. Plain lines use the fitted rule, which handles leading.
- **iOS 17:** the package minimum, but no iOS 17 runtime is installed on the build host. Parity is measured on iOS 26.3 (3x and 2x) and iOS 18.5 only; on iOS 17 TK2 is unverified (the pre-26 eligibility rules apply; list text stays on SwiftUI before iOS 26, §3 PR 2).
- **Code canvas admission caps (PR 3; provisional).** A TK2 row draws into one untiled canvas as large as the whole row, so a code row's canvas grows with the block, not with the viewport. A code block is therefore admitted to TK2 only when a conservative bound on its canvas is within two caps: `TextKit2Scope.maximumCodeCanvasDimension`, 8,192 px per dimension, and `maximumCodeCanvasBytes`, 16 MiB nominal (bound width × bound height × 4 bytes). A block over either cap stays on SwiftUI exactly as on main. **Both caps are provisional engineering admission caps chosen by judgement. They are not measured safe limits of any device, and they are not a memory guarantee:** the nominal bytes are not the allocation, several admitted rows can be alive at once and nothing caps their sum, and the simulator does not attribute canvas backing stores to the app at all (the canvas bullet above). PR 3 made no physical-device run, so the real backing-store cost of an admitted code canvas against SwiftUI's own layers is not measured; that measurement is due before TextKit 2 is turned on by default. E3, the canvas ladder (`TextKit2CodeMeasureFirstTests`, 3x on iOS 26.3 and 18.5, `CODE_E3` lines in `<data>/step7-tests/r2a-3x-code.log`): a tall block of 12 columns at 25 % of the cap drew 379 × 1,863 px against its bound of 381 × 1,986; at 100 %, 379 × 8,067 px against 381 × 8,190 (11.9 MiB nominal), with the far-right ink and the last line's ink in the TK2 bitmap; at 150 % it was not admitted and had no row. A wide block of two lines drew 2,018 × 147 px against 2,020 × 270 at 25 % and 8,166 × 147 px against 8,168 × 270 at 100 %, and was not admitted at 150 %. E3 renders the layer on the CPU (`CALayer.render(in:)`), so it does not show that the compositor displays an 8,192 px layer, and it records no memory figure.
  - **The bound** (`TextKit2Scope.codeCanvasEstimate`): `pixelWidth = ceil(maxLineUTF16 × advance × scale) + 2` and `pixelHeight = ceil(((lineCount + 2) × lineHeight + 2 pt) × scale)`. `maxLineUTF16` and `lineCount` come from the prepared shape. `advance` and `lineHeight` (ascent + descent + the leading when it is positive) are measured once per (font spec, size category, legibility weight) from the font `TextKit2FontResolver` resolves for the code string's own prepared spec, the font the text builder uses (`TextKit2CodeMetrics`). At Large the default code font measures an advance of 10.5088 pt; its line pitch is 22.0 pt on both engines, and the bound's `lineHeight` is in (21.967, 22.0] pt (C27). The reserves: 2 px of width (the pixel-snapped frame; the typesetter's sum of advances against the product), two lines of ink (one above the first line box, one below the last) and 2 pt of rounding (the row rounds its canvas's vertical extent outwards to whole points).
  - **The admitted cohort.** A bound is stated only where it is conservative: every scalar printable ASCII or LF, at least one character on a line, in one monospaced font whose 95 printable ASCII glyphs are its own, advance alike within 0.01 pt and ink within half a line of the ascent and descent. The inputs must be finite and positive, a line at least two pixels tall, and the arithmetic must fit an `Int`, which is checked without trapping. Anything else has no bound and stays on SwiftUI.
  - **The invariant** is `actual canvas ≤ admitted bound ≤ cap` in each dimension. `TextKit2CodeCanvasBoundTests` and `TextKit2CodeFallbackTests` assert it: exactly at each limit, one pixel over, very wide and short, very narrow and tall, Bold Text, custom monospaced specs (bold, italic, another text style) and size-category changes, and for rows really laid out. It rests on four run-time assumptions: the resolved font is fixed pitch, with no tracking beyond what the typeset sample shows and no pair kerning that widens a line; the baseline pitch exceeds `lineHeight` by less than the two reserve lines cover (at Large by less than 0.033 pt a line, against a reserve of 44 pt); a fragment's rendering surface stays within one line of its line boxes; and `CTFontGetBoundingRectsForGlyphs` returns a real rectangle (if it does not, every code block is gated: safe, but nothing is admitted). Measured: in the parity matrix on 3x and 2x iOS 26.3 and on iOS 18.5 every admitted row's actual canvas was within its bound (the tightest by 2 px), and the default code font passed its self-check at every size and weight the matrix covers. The assumptions are measured only for the default code font and the suites' custom monospaced specs; a theme with another monospaced font relies on the self-check alone.
  - **The same code needs a larger canvas at a larger text size**, so ordinary blocks cross the caps as the size grows, and many stay on SwiftUI at accessibility sizes. Measured on 3x iOS 26.3 (`cand-059a4db`, `<data>/step8-app/c25-cand-059a4db/table.tsv`), code-dense admitted / gated of 600 at `-fontSizeStep` 0 to 4: 582 / 18, 499 / 101, 478 / 122, 441 / 159 and 360 / 240 (predicted from the measured metrics before the run: 582, 494, 471, 437 and 345 admitted).
  - **A worked figure.** The largest code block of the stress fixtures, 8 lines of 39 columns, at Large on 3x: bound 1,232 × 666 px, about 3.1 MiB nominal, at the measured metrics. A row of the parity suite's eight-line sample (8 lines of 38 columns) drew 1,199 × 543 px against its bound of 1,201 × 666.
  - **Containers (PR 4).** The caps are per code block. They do not bound an eager container that holds many code blocks; the container stage assesses that aggregate itself. **PR 4's assessment:** no aggregate cap. The eager multi-code probe (`TextKit2NestedCodeTests.eagerMultiCodeContainer`, seven code blocks in one quote at 2x) builds 6 code rows, admits 6 and gates 1, and sums 9,381,312 nominal canvas bytes (about 8.9 MiB); the shape that would hold more (code beside prose in a panel, containers-parity 0.77) stays SwiftUI by the panel shape rule. A container-level cap, if one is needed, is a design of its own (§6.6, eager expand bodies).
- **The shipping path carries two more attributes (PR 3).** Preparation stamps the code font spec and the code shape on every code string with the switch ON or OFF, so arm B carries them: one pass over each code block's scalars at preparation time, and nothing at view time (the SwiftUI arm reads no new environment value and computes nothing in the leaf). Measured alone on macOS, stress-5k prepares in 0.1021 s against main's 0.0996 s (`<data>/prep-timing/report.md`). In the app, the `pr3` gate's arm B rows against the anchor measure it (§8.3).
- **A code row is one canvas for the whole block (PR 3).** A tiled or viewport-clipped canvas is the real fix for large code blocks and is out of scope; until then such blocks stay on SwiftUI by the caps above.
- **Tall eager container bodies (PR 4; measured, no cap).** A container's children are one eager `VStack` inside one lazy row (ADR §4), so opening an expand materialises its whole body at once, each eligible leaf a TK2 row with its own canvas. A 300-row expand body (`TextKit2ContainerCostTests.tallExpandBodyMount`, M1 and M5): 300 conversions and 300 layouts on a reopen of the cached body and on each ON flip, measured in spans with no suspension (k = 1, no issue 10 signature; the first open prepares off the main actor and read 310 with other suites converting in parallel). Summed nominal canvas bytes of the open body at 3x (M5, by the canvas formula, an upper bound): 131,817,204 B (125.7 MiB, about 440 KB a row in a 390 pt window). ## 7. Links and accessibility (TK2 rows)

- **Links:** a `UITapGestureRecognizer` (only on rows whose text has a link) with `cancelsTouchesInView = false` that never swallows vertical flings. A tap opens a link only if the touch begins inside that link run's glyph rects (the union of its line-fragment segment rects, taken from the row's TextKit 1 stack — the engine that laid the text out), not "nearest character"; the link is resolved where the touch began, so drift within tap slop still opens it. Delivery goes through the SwiftUI `openURL` action, so hosts keep control. Native TextKit 2 links: PR 6. Linked list text (PR 2) uses the same row and the same handling.
- **Accessibility:** the row is one element — label = plain text, traits `staticText` (+ `header` for headings), value `nil` — plus one "Open link <host>" custom action per link range. A list leaf (PR 2) is the same element, one per leaf; list markers stay SwiftUI chrome (§3, PR 2 "Accessibility").
- **Heading level (PR 1 residual, not fixed):** the SwiftUI `.accessibilityHeading` modifier on `RichTextBlockView` covers the SwiftUI arm only; it does not carry the level to the TK2 row, which is its own UIKit element. VoiceOver on iOS 27.0 says "Heading" with no level for a TK2 heading where the SwiftUI arm says "Heading level 2" (`<data>/p4-uitests/runs/r14-voiceover-ios27.xcresult`, PR 2's data directory); the row sets the `header` trait only (`TextKit2RowView.swift:167`). Setting `.accessibilityTextHeadingLevel` over the row's `accessibilityAttributedLabel` (8faf040) changed nothing: VoiceOver ignores that text attribute on an element label (`r27-voiceover-ios27.xcresult`), so a76736f reverted it. The iOS 27.1 SDK has no public element-level heading level. `ListRendererUITests.testVoiceOverTraversalOfTasksAndDecisions` compares the heading without its level and pins the level as a strict `XCTExpectFailure`, so a fix fails the test as an unexpected pass (9246d99, `r28-voiceover-ios27.xcresult`). Candidate route: let SwiftUI own the element so `.accessibilityHeading` applies, keeping the `tk2-row:` identifiers and rebuilding the "Open link" actions as SwiftUI actions (`<data>/phase5/heading-level-followup.md`).
- **Code rows (PR 3):** a TK2 code row is the same single element: label = the code's plain text, traits `staticText`, value `nil`, and no custom action, because linked code is not eligible and so a code row carries no tap recognizer. The language badge and the Copy button ("Copy code") are SwiftUI chrome under either engine (§3, PR 3 "Accessibility").
- **Container rows and captions (PR 4):** a TK2 leaf inside a container, and a TK2 caption, is the same single element as a top-level row: label = plain text, traits `staticText` (+ `header`), value `nil`, and an "Open link <host>" custom action per link; linked container text is TextKit 1-backed (`linkedContainerLeaves`, `containerTextKit1DrawCount`). The container's own accessibility is SwiftUI chrome and unchanged: the panel icon hidden, the extension placeholder one labelled group with its children contained (`testPanelExtensionPlaceholderStaysOneLabelledGroup`), the expand title a button with value "Expanded"/"Collapsed" (`testExpandValuesAndOpenedBodies`). Reading order in layout columns is column-major on both arms (`TextKit2ContainerColumnTests.columnOrderIsColumnMajor`; VoiceOver traversal checked stacked on iOS 27.0, `testVoiceOverColumnOrder`, equal utterances in both arms). Link taps in container rows open the exact URL once (`testPanelLinksRouteExactURLAndRejectBlankHref`, `testColumnsLinkRoutesExactURL`); a caption's link and the media box's link hit separate regions (`testCaptionImageAndLinkTapsHitSeparateRegions`). A task marker in a nested list in a quote dispatches once (`testNestedListTaskInQuoteDispatchesOnce`).

## 8. Running the gates

Every PR runs all of these against main. Proof artefacts (screenshots, perf CSVs, videos) live outside the worktree and are never committed.

No CI is configured for this repository; no hosted-check result is claimed. Every result in this section is a local run on a named simulator, with its evidence path. A package-only hosted run would not establish the renderer anyway: the TextKit 2 sources and suites compile only where UIKit exists.

**What it can and can't catch** (per PR description too):
- Catches: stalls (the 27/27 kitchen-sink stall at 940 ms/s, the post-boot 197 ms/s), sustained ≥ 1 % drops, ≥ 15 % memory growth, ≥ 15 % kitchen-sink READY (and list-dense READY in `pr2`).

- **Paired predecessor supplement, D against C (`pr3`).** It asks whether this stage added to the debt rows. `--app-d` runs it inside the named run, after the A/B/C trials, so one `plan.json` pins the D, C and fixture digests before the first trial and C is provably the gated binary. The method is frozen in the design before any candidate timing. Per fixture and metric (dropped frames, dropped rate, hitch ratio) it takes the paired differences C − D; the sensitivity is the gate's own +2 dropped frames (for the rate and the hitch ratio, the same 2 frames converted with D's median frame count); and it computes one-sided 95 % distribution-free bounds on the median difference (with 5 pairs: the smallest and the largest difference). Upper bound ≤ sensitivity: `NO-ADDED-REGRESSION`. Lower bound > sensitivity: `ADDED-REGRESSION`. Otherwise `INCONCLUSIVE`, never "unchanged". So with 5 pairs a row is cleared only when every pair is within +2 frames. - **Host (firstmate policy):** quiet = 1-min load ≤ 4.0 and no non-simulator process above 100 % CPU. After the settle (300 s when the run booted the device) the driver samples the host every 30 s for up to 20 min (`--host-poll`, `--host-wait`) and starts when it is quiet, or after the wait regardless. `plan.json` records the last sample and the wait; every trial row records its start time, load and busiest processes. A run that was not quiet at the start or in any counted trial is **HOST-BUSY**: its PASS counts; its FAIL is reported as `FAIL-HOST-BUSY` (exit 6) and is re-run once at the next quiet window before it counts as a FAIL. Nothing is ever killed or reniced.
- **Fail closed:** a result counts only with every declared pair present, every metric finite, exit 0, the expected `READY` line, and the installed sha256 and argv matching the arm. The summarizer reads the design and the pilot flag from `plan.json`, never from its own flags, and marks a reduced plan INCOMPLETE. Precedence: candidate crash → FAIL; invalid trial, baseline failure or A ceiling breach → INVALID; candidate failure → FAIL; too few pairs → INVALID; calibration INCONCLUSIVE; statistical or ceiling failure → FAIL; PILOT; INCOMPLETE; PASS; then a FAIL on a HOST-BUSY run → FAIL-HOST-BUSY. Exit codes: PASS 0, FAIL 1, INVALID/REFUSED 2, INCONCLUSIVE 3, PILOT 4, INCOMPLETE 5, FAIL-HOST-BUSY 6.
- **Reruns:** every verdict is appended to `perf-ledger.jsonl` beside the run directory. A FAIL with the same candidate binaries and design is never rerun (REFUSED); a FAIL-HOST-BUSY allows one rerun, and a second FAIL-HOST-BUSY for the same binaries counts as FAIL; after two INCONCLUSIVE/INVALID runs the next is REFUSED. Pilots do not count. A design that includes another (`pr2` includes `pr45`) is also REFUSED after a FAIL of the included design for the same candidate binaries, because it re-measures those fixtures.
